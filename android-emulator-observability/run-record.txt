Defect (verified against `git show HEAD` on a clean tree — no local edits):
`Java_dev_meeterm_terminal_MeetermNative_runtimeBrowseRespondHostKey`
(native/meeterm-core/src/jni.rs ~L990-1013) declares `accept: jboolean` and
passes it verbatim into `meeterm_runtime_browse_respond_host_key`
(native/meeterm-core/src/ffi.rs L1260), whose signature takes `accept: u8`
(`if accept > 1 → InvalidArgument`; then `runtime_browse_respond_to_host_key(.., accept != 0)`).
jni crate pin is `jni = "=0.22.4"` where `jboolean` resolves to `bool`,
so the call is a type mismatch.

Why it slipped through: `mod jni` is `#[cfg(target_os = "android")]` in
src/lib.rs, so host `cargo check` / `cargo test` never compile the JNI layer.
Verified: `cargo check` on host PASSES on this commit (10.9s). The break is
exclusive to Android target compilation (`cargo ndk` / gradle buildRustAndroid).

Sibling site is fine: `sshRespondHostKey` (jni.rs ~L1173) passes its
`accept: jboolean` to `crate::ssh::respond_to_host_key` which accepts bool —
only the new browse wrapper mismatches.
